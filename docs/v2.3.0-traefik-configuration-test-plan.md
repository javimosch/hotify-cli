# hotify-cli v2.3.0 Traefik Configuration Test Plan

## Overview
This test plan addresses the obstacles encountered during cmdcenter deployment on dk1 (May 2026) and ensures hotify-cli can handle Traefik configuration robustly in future deployments.

## Background

### Issues Encountered (cmdcenter deployment)

1. **ACME "Domain Not Defined" Error**
   - Traefik rejected the domain configuration with: `error while parsing rule Host(cmdcenter.intrane.fr): cmdcenter.intrane.fr is not defined`
   - Required manual fix: Adding explicit domain specification in TLS configuration

2. **ACME Challenge Type Conflicts**
   - Original configuration had both DNS and HTTP challenges configured
   - Caused conflicts and certificate generation failures
   - Required manual fix: Switching to HTTP challenge only

3. **Service Reload Not Supported**
   - `systemctl reload traefik` failed with "reload is not supported for this unit"
   - Required manual intervention: Using `systemctl restart traefik` instead

4. **Dynamic Configuration Not Picked Up**
   - Changes to dynamic.yml didn't take effect without restart
   - Required manual restart despite `watch: true` being enabled

## Test Cases

### TC1: ACME Domain Specification

**Objective**: Ensure hotify-cli generates proper domain specification in Traefik dynamic configuration

**Steps**:
1. Initialize hotify-cli with Cloudflare token and domain
2. Add a new app with subdomain
3. Run `hotify-cli setup-traefik --id <app-id>`
4. Check generated `/etc/traefik/dynamic.yml`
5. Verify the configuration includes explicit domain specification:
   ```yaml
   tls:
     certResolver: letsencrypt
     domains:
       - main: app.example.com
   ```

**Expected Result**:
- Dynamic configuration includes explicit domain specification
- No "domain not defined" errors in Traefik logs
- SSL certificate generates successfully

**Test Data**:
- App ID: test-app
- Domain: test.example.com
- Port: 3000

### TC2: ACME Challenge Type Selection

**Objective**: Ensure hotify-cli allows choosing between HTTP and DNS challenges

**Steps**:
1. Add a new app configuration
2. Run `hotify-cli setup-traefik --id <app-id> --challenge-type http`
3. Verify `/etc/traefik/traefik.yml` uses HTTP challenge
4. Repeat with `--challenge-type dns`
5. Verify configuration uses DNS challenge

**Expected Result**:
- `--challenge-type` flag is accepted
- Traefik configuration uses the specified challenge type
- Only one challenge type is configured (no conflicts)

**Test Data**:
- Challenge types: http, dns
- Default: http (if not specified)

**Test Data**:

### TC4: DNS Record Existence Check

**Objective**: Ensure hotify-cli checks for existing DNS records before attempting creation

**Steps**:
1. Create a DNS record manually via Cloudflare dashboard
2. Run `hotify-cli setup-dns --id <app-id> --ip <ip>`
3. Verify hotify-cli detects existing record
4. Verify it skips creation or updates appropriately

**Expected Result**:
- hotify-cli checks for existing DNS records
- Skips creation if record exists with correct IP
- Updates record if IP differs
- No duplicate record errors

**Test Data**:
- Pre-existing DNS record: test.example.com → 92.113.145.178
- New app with same domain
- Test with matching and non-matching IPs

## Implementation Requirements

### Required Features for v2.3.0

1. **ACME Challenge Type Selection**
   - Add `--challenge-type` flag to `setup-traefik`
   - Support `http` and `dns` values
   - Default to `http` for simplicity

2. **Explicit Domain Specification**
   - Include `domains:` section in generated TLS configuration
   - Use proper YAML syntax with backticks

3. **Reload/Restart Detection**
   - Detect systemd service reload capability
   - Fall back to restart when reload not supported
   - Add `--force-restart` flag to override detection

4. **DNS Record Existence Check**
   - Check Cloudflare API for existing records
   - Skip creation if exists with correct IP
   - Update if exists with wrong IP

5. **Configuration Validation**
   - Validate configuration before applying
   - Provide clear error messages
   - Prevent invalid configurations

6. **Enhanced Error Handling**
   - Better error messages for common issues
   - Suggested fixes where applicable
   - Retry mechanisms for transient failures

### Optional Features

1. **Configuration Dry Run**
   - `--dry-run` flag to preview changes
   - Show what would be modified
   - Validate without applying

2. **Rollback Capability**
   - Backup configuration before changes
   - Rollback on failure
   - Manual rollback command

3. **Configuration Diff**
   - Show differences between current and new configuration
   - Highlight critical changes
   - Interactive confirmation
