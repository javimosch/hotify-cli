### Critical Bug Discovered and Fixed
**Daemon Process PID Tracking Issue (FIXED):**
When `start` command executed `sh -c <command>`, it tracked the shell process PID. For daemon apps that double-fork (like cmdcenter uses setsid), the shell exits immediately and the actual daemon re-parents to PID 1, making the tracked PID invalid.

**Fix implemented:** Two-strategy resolver in `resolveActualPID()`:
1. `/proc` tree walk — finds leaf child of shell (works for single-fork processes)
2. Port-based lookup via `ss` — finds PID bound to app's configured port (works for double-fork/setsid daemons)

**Verified working:**
```
hotify-cli start --id cmdcenter --local
→ {"pid":911432,"shell_pid":911427,...}  ← different PIDs, daemon PID correct
→ ps confirms: PID 911432 = /usr/local/bin/cmdcenter
```

### Remote Daemon Issue
**Problem:** server.go doesn't have the PID tracking fix from local_ops.go
- Remote start returns success but doesn't actually execute the command
- PID stays 0 after remote start
- Remote pause/resume fail when PID is 0
- Remote pause/resume work when valid PID is set by local start (daemon reads from config)

**Impact:** Remote mode cannot start processes or track their PIDs
- Users must use local mode for actual process management
- Remote mode only works for operations on already-running processes (with valid PID in config)

**Fix needed:** Apply the same two-strategy PID resolver to server.go:
1. Add `findDeepestChild()`, `findPIDByPort()`, `resolveActualPID()` to server.go
2. Update `handleAppStart` in server.go to use `resolveActualPID()`
3. This would give remote mode the same daemon-friendly PID tracking as local mode
